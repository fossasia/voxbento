## Legacy API authentication

Trusted integrations can exchange the production `BOOTH_ACCESS_TOKEN` at `/api/auth/token` for a legacy API JWT. The credential and resulting JWT have global scope across the applicable protected `/api/events/...` endpoints, not event-specific scope, so operators should generate the credential with `openssl rand -hex 32` and share it only with trusted integrations. This global credential does not grant access to unrelated application routes or bypass separate authorization checks; participant tokens, user JWTs, and event-scoped API keys remain subject to their own event, room, and language scopes.


Voxbento is built on a single guiding principle: the audio path should be as short and as direct as possible. Rather than routing interpreter microphone audio through application servers, Voxbento sends audio straight from the interpreter's browser to MediaMTX — an open-source media server — and from there straight to each listener's browser. The Voxbento coordination portal sits alongside that path to handle coordination, but it never touches the audio itself.

## The Interpretation Pipeline

Here is how audio travels from the speaker on stage to a listener's headphones, step by step:

### Floor audio: the speaker enters Jitsi

The presenter or speaker joins a self-hosted Jitsi Meet session. This session carries the event's floor audio — the source language that interpreters listen to and translate.

    Voxbento embeds the relevant Jitsi session as an iframe directly inside each interpreter's booth page. The interpreter monitors floor audio and video from within the same browser tab where they will broadcast their translation, which keeps the workflow contained and the latency low.

The bundled Jitsi `stable-11248` services run rootless with read-only container
filesystems. Persistent web and Prosody state is isolated in writable storage
volumes, while runtime data lives in temporary filesystems. The browser-facing
ports remain `8080`/`8443`, even though the hardened web container listens on
unprivileged ports `8000`/`8443` internally.
  ### Interpreter audio: mic capture and WebRTC publish

When the interpreter clicks **Go Live**, the browser calls `navigator.mediaDevices.getUserMedia` to capture microphone input. Before the audio leaves the browser, the browser's built-in DSP stack applies:

    - Echo cancellation (to prevent Jitsi floor audio from bleeding into the interpreter's mic)
    - Noise suppression
    - Auto gain control

    The processed audio track is added to an `RTCPeerConnection`. The browser then performs a WHIP handshake — a standard HTTP POST that negotiates the WebRTC session with MediaMTX. After the handshake, audio flows over the established WebRTC media connection directly to MediaMTX.

    :::info
The audio path goes directly from your browser to MediaMTX and then to listeners — Voxbento's coordination portal is only involved in booth state, role checks, and captions, and never relays interpreter microphone data.
:::
  ### MediaMTX: ingest and remux

MediaMTX terminates the WebRTC connection from the interpreter's browser, decodes the audio, and makes it available on a named path that corresponds to the booth's identity:

    ```text
    {event_slug}/{room_id}/{language_code}
    ```

    For example, the English booth in room 14 at PyCon 2026 occupies the path `pycon2026/14/en`. The WHIP and WHEP URLs for that booth follow the pattern:

    ```text
    # Interpreter publishes to:
    {mediamtx_base}/pycon2026/14/en/whip
    
    # Listeners connect to:
    {mediamtx_base}/pycon2026/14/en/whep
    ```

    MediaMTX holds these paths open even when no interpreter is currently publishing, so listener connections are never dropped between handoffs.
  ### Listener delivery: WHEP (primary) and HLS (fallback)

Listeners connect to the WHEP endpoint for their chosen language. WHEP (WebRTC HTTP Egress Protocol) is the mirror of WHIP — it negotiates a WebRTC session from the server side and streams audio to the listener's browser with sub-second latency.

    For devices that do not handle WebRTC reliably, MediaMTX also produces HLS segments on a separate port. The listener page loads hls.js and falls back to HLS automatically when WHEP is unavailable. HLS introduces roughly three seconds of additional latency but works on virtually any device.

    :::tip
You do not need to configure the fallback manually. The listener page tries WHEP first and switches to HLS transparently if the WebRTC negotiation fails.
:::

Rooms can also define an optional listener-side audio synchronization delay. This is useful when attendees are watching delayed livestream video, delayed captions, embedded conference players, or external media while listening to Voxbento audio. For example, use `1000` ms for a one-second caption delay, `2000` ms for a lightly delayed player, `5000` ms for a typical embedded stream, or `8000` ms for a platform with a larger broadcast buffer. When the room delay is `0` ms, listener playback uses the same direct WHEP-to-HTML-audio path as normal and adds no Web Audio graph or extra latency.

In the organizer workspace, room management includes server-side search to quickly filter rooms by name within an event using case-insensitive matching against the room display name, displaying a clearable empty state when no rooms match the query.

## Organizer and System Administration Routes

Event management and system administration use separate public URL namespaces:

- `/workspace/...` is the event workspace for `event_owner` users. It contains event, room, booth, membership, transcription, translation, and event API-key management scoped by the existing role checks.
- `/mission-control/...` is the room-scoped operational surface for `room_coordinator` users.
- `/admin/...` is reserved for Admins and contains system-wide views such as user and developer-account management.

Both namespaces use the same underlying management handlers, so the route split does not duplicate event-management behavior. Existing organizer bookmarks under `/admin/events/...` receive a temporary redirect to the corresponding workspace URL with their query string and HTTP method preserved. The OAuth routes remain under `/oauth/...`; shared-organizer authorization and token lifecycle behavior are therefore unchanged.

Room deletion checks that the requested room belongs to the event specified in the workspace URL before removing it and its dependent booths, invites, and memberships. An unknown room or a room from another event returns HTTP 404 without deleting any data.

## The Transcription & Translation Pipeline

When live captions or translations are enabled, Voxbento spawns background workers to process the audio in real-time. This pipeline supports both **Booth Audio** (interpreters) and **Floor Audio** (the main conference).

### Floor Audio Capture
To transcribe or translate the original speakers without requiring external integrations, the system launches an isolated **Floor Bot** (`floor-bot`). This headless Chromium instance silently joins the Jitsi meeting, captures the live audio, and pushes it to MediaMTX via RTSP, making it accessible to the transcription workers just like a regular booth.

Event owners control the bot as a managed **Meeting source** on the room page. `rooms.meeting_agent_enabled` stores the desired state; `portal/meeting_source.py` compares it every two seconds with the bot's `/status` and the MediaMTX floor path. It restarts a failed agent with back-off up to `MEETING_AGENT_MAX_RESTARTS` times, starts the floor transcription worker only after audio arrives, and stops agents that no rooms want after a portal restart. The room has one floor owner: the meeting agent or program ingest. Switching between them requires confirmation. Meeting URLs can carry Jitsi credentials, so they are never logged or returned in status responses.

Venues without a hardware encoder can send floor audio from a browser instead. The room page opens a dedicated **Program audio sender** tab that publishes the chosen sound-desk input over authenticated WHIP with a short-lived session secret. Because the stream lives in that tab, the rest of the console can be used freely. After network drops the sender retries with back-off; it stops and reports an error when the sign-in expires or another source owns the floor. It keeps the screen awake, can mute without giving up the floor, and offers a local sound check (level hint plus record-and-play-back) that never reaches listeners.

### Pipeline Steps

Floor-bot dependency upgrades are checked separately in CI: the Playwright SDK
must match the bundled browser version, and the real container must launch
Chromium, publish a local audio tone through PulseAudio and the production FFmpeg
Opus/RTSP command, and decode it from a local MediaMTX server. The check requires
sustained energy at the fixture's 440 Hz frequency; brief startup noise cannot
declare capture healthy. CI also
checks a 900 MB compressed base-image budget for Linux amd64 before pulling
layers. These checks cover browser and audio dependencies without an external
Jitsi session; they do not validate a deployment host's available disk space.

1. **Audio Ingest:** The worker uses FFmpeg to pull the live audio stream from MediaMTX via RTSP (`rtsp://mediamtx:8554/{event_slug}/{room_id}/{language_code}` or `rtsp://mediamtx:8554/{event_slug}/{room_id}/floor`).
2. **Transcoding:** FFmpeg transcodes the audio to PCM S16LE (mono, 16kHz or 24kHz depending on the provider) and pipes it to the selected `TranscriptionProvider`.
3. **Speech-to-Text (Transcription):** The provider sends audio to an AI service (OpenAI, Deepgram, ElevenLabs, NVIDIA, or Local Whisper). The `CaptionAggregator` receives raw text, splitting sentences and instantly broadcasting partial updates to listeners (`/ws/captions/{channel_id}`).
4. **Finalization:** Once a full sentence is formed, the aggregator saves it to the database as a canonical `transcript_segment`.
5. **Text-to-Text (Translation & AI Interpretation):** If target languages are enabled, the Translation Worker detects the finalized segment and generates translations using LLMs (Anthropic, OpenAI, Groq, Gemini) or local NLLB. Translation prompts dynamically integrate the room's configured **AI interpreter persona** and **interpretation style**, as well as matching domain terms from the room's **AI vocabulary glossary**, ensuring consistent, conference-grade terminology.
6. **Broadcast:** Translations are saved to the database and immediately broadcast as `translated_caption` events via the target booth's caption feed (`/ws/captions/{booth_id}`).

7. **Text-to-Speech (TTS):** If the room has "Floor Audio TTS (Direct Push)" enabled, the `TTSWorker` instantly receives the finalized translated text and synthesizes speech using the room's configured provider — either **Deepgram Aura** (cloud WebSocket) or **Supertonic** (self-hosted, in-process ONNX).
8. **TTS Audio Delivery:** The synthesized audio is streamed to listeners in structured binary bundle messages (1-byte version, 4-byte header length, JSON metadata header, and optional 24 kHz 16-bit mono PCM payload) over an authorized subscription WebSocket (`/ws/tts/{room_id}/{language_code}/{booth_id}`). Listeners receive translated speech natively via the Web Audio API with sub-second latency, scheduled smoothly by `audio-scheduler.js` without relying on WHEP.

:::info
Transcription, Translation, and TTS workers are isolated from the main audio path. If an API provider lags, fails, or drops chunks, the core interpretation audio remains perfectly stable and unaffected.
:::

## Booth Identity

Every booth in Voxbento is uniquely identified by three coordinates:

| Coordinate | Format | Example |
| --- | --- | --- |
| `event_slug` | Lowercase alphanumeric and hyphens, 1–64 characters | `pycon2026` |
| `room_id` | Non-negative integer representing the room / stage | `14` |
| `language_code` | ISO 639-1 two-letter code | `en` |

These values combine to form the **MediaMTX path** (`pycon2026/14/en`) and the **booth ID** (`pycon2026-14-en`). Both are derived at runtime — there is no separate stored URL. If you change the event slug, room, or language code, the derived URLs update automatically.

Administrators can search the event list by either slug or display name. Filtering is applied before pagination so page counts and results stay in sync. Search treats `%` and `_` literally, pagination URL-encodes reserved characters such as `&` and `#`, blank queries show all events, and out-of-range pages open the last filtered page.

## Interpreter Handoff

In a professional interpretation setting, interpreters rotate every 20–30 minutes to prevent fatigue. Voxbento handles this transition without interrupting listeners.

Here is what happens when a room_coordinator switches the active interpreter:

1. The room_coordinator clicks **Set Active** next to the incoming interpreter in the booth.
2. The portal updates the active interpreter state and notifies all booth participants over WebSocket.
3. The incoming interpreter's browser asks the portal for a single-use publish ticket over its booth WebSocket (`booth:request-publish-ticket`) and sends it as `Authorization: Bearer` on its WHIP request.
4. MediaMTX is configured with `overridePublisher: yes` — it immediately accepts the new publisher and disconnects the outgoing interpreter's WHIP session.
5. All existing WHEP listeners receive the new publisher's audio within approximately one to two seconds. Their `RTCPeerConnection` stays open throughout; MediaMTX routes the new track into it automatically.
6. **Transcription Continuity:** The backend background transcription worker (FFmpeg) continuously retries pulling from the RTSP stream. Even if the stream drops for a few milliseconds during the handoff, the worker aggressively reconnects, ensuring zero loss of translation pipeline state.

:::info
Listeners on the HLS fallback path experience a longer gap during handoff — roughly 10–15 seconds — while hls.js recovers from the muxer reset that occurs when the publisher changes.
:::

## Roles

Voxbento defines a clear privilege hierarchy across live operations:

### Room Coordinator

Oversees the room's booths from Mission Control. Assigns which interpreter is active, initiates handoffs, and monitors participant state. Room coordinators can participate in booth chat and can also publish audio when designated as the active broadcaster.

### Interpreter

Monitors floor audio via the Jitsi iframe and publishes translated audio to MediaMTX via WHIP when designated as the active interpreter. Only the active interpreter can go live — all others remain in standby.

### Listeners

Listening is not a role. Listeners receive the interpreted audio stream from MediaMTX via WHEP or HLS. They connect to the event's public listener page and choose a room and language — no login required by default.
  

## Live Captions

When transcription is enabled for a booth, Voxbento pipes the active interpreter's audio to a transcription backend (Whisper, OpenAI, Deepgram, ElevenLabs, or NVIDIA Riva) and broadcasts the resulting text to all listeners in real time.

Captions are delivered over a dedicated WebSocket endpoint:

```text
/ws/captions/{booth_id}
```

For example:

```text
/ws/captions/pycon2026-14-en
```

Listeners connected to the caption WebSocket receive transcription segments as they are produced. The caption stream is independent of the audio stream — listeners can receive captions even while audio is playing through WHEP or HLS.

## Shared header and user menu

Every signed-in page (Admin, My events and its event pages, My booths, Mission
Control, Account, Developer API) renders the same header from `_app_header.html`:
the VoxBento logo with the name of the current area, the area's page links, and
the user menu. `portal/user_menu.py` builds the menu from the request principal: My
events, My booths (only for interpreters, given for an event or a booth), Account,
Developer API (only with an approved developer app), Admin (only for Admins) and
Logout, with the current area highlighted. A router dependency loads the principal
once per request so templates never query the database.

The interpreter booth is a work screen, so it uses a compact bar instead: the
language, room and event names, the connection state, the same user menu and
**Leave**, and no site footer. **My booths** (`/interpreter`) lists the person's
booths by event and room, with **Enter booth** (and **Mission Control** for
coordinators) next to a microphone and connection check.

**Mission Control** (`/mission-control/{event}/`) shows one section per room the
person may run. Each room shows its floor captions' state with Start and Stop
(through `/api/rooms/{room_id}/floor-transcription/*`), and each booth card shows
who is in the booth and who is live, a listen-in slider, Go live / Stop broadcast
and **Open booth**. The owner's room page is split into tabs (Overview, Floor
source, Captions & translation, Settings); the open tab is remembered per room so
saving a setting returns to it, and without JavaScript every section shows in order.

**My events** at `/workspace/` (`portal/my_events.py`) lists every event the
person has a role in, combining event, room and booth memberships into one card
per event: "Event owner", "Room coordinator · Room 1", "Interpreter · Grand Hall ·
Chinese", each with a button to where they work. Deleted events are hidden.

## Account page

`/account` is about the person themselves, in four sections. **Profile** changes
the display name (`POST /account/profile`); the email is shown but can't be
changed there. **Hosting events** shows Request access, the open request
waiting for review, or a link to My events. **Developer API** shows the
application state from `developer_accounts`: apply (links to `/developer`),
pending with its date, approved with a link to the Developer API page, or
rejected/suspended. **Sign-in** changes the password (the current one is
required), sets a first password, or removes it so the person signs in with
email links only. Event, room and booth roles are listed on My events instead.

## Admin Users pages

`/admin/users/` lists every account with a search, a **Show** filter (All users,
Admins, Hosting access, Deactivated, Email not verified) and on/off switches for
**Hosting access**, **Admin**, **Active**, and **Email verified** in each row, changed in place without a
page reload. Each switch posts to `/admin/users/{id}/access`; if the server refuses
a change, the switch flips back and the reason is shown. `/admin/users/{id}/` shows
the person's platform access, their roles in events (read-only, since each event's
owners manage roles), the events they own, account facts and a danger zone.
Deleting an account requires typing its email address.

`portal/user_admin.py` holds the rules every path follows: an Admin can't change
their own Admin or Active status or delete themselves, VoxBento always keeps at
least one active Admin, and hosting access is only granted to active accounts that
have finished setting up (others get an invitation instead).

## Administrative access

Administrative access is tied to registered user accounts rather than a shared
deployment password. Everyone, including site-wide administrators, event owners
and room coordinators, signs in at `/login` with their email address and receives
the normal `user_token` session cookie. The sign-in page asks for the email first:
known addresses continue to a password or magic link, and unknown addresses go to
`/register` with the email pre-filled. The retired `/admin/login` URL redirects to
`/login?next=/admin/`. Event owners and room coordinators receive only the scoped access their
memberships allow. Operators should maintain at least two active administrator
accounts; the [admin-login migration guide](https://github.com/fossasia/voxbento/blob/dev/docs/admin-password-removal-migration.md)
documents the controlled recovery procedure.

## Hosting access requests

Creating events requires hosting access (`users.can_host`). Signed-in users without
it request access from `/account/hosting-request`; the form is pre-filled with
their name and email and stores a row in `hosting_requests` linked to their
account. A partial unique index allows only one open request per user. Each new
request emails the team address in `HOSTING_REQUESTS_EMAIL`, and the Account page
shows the request as waiting for review until it is handled.

Admins see open requests on the **Requests** tab of `/admin/hosting-access/`; the
"Hosting access" menu item shows how many are open, and the "Dev Accounts" item likewise shows how many Developer API applications are waiting for review. Granting sets `can_host`,
closes the request as `granted` and sends the "hosting access granted" email.
Declining requires a reason, closes the request as `declined` and emails the
reason to the person, who can then send a new request. Granting hosting access
any other way (the user page toggle or an accepted hosting invitation) also
closes an open request.

## Transactional email

VoxBento queues transactional email in the same database transaction as the
action that caused it. The outbox worker leases messages, retries transient SMTP
failures, and preserves records when SMTP is not configured. Platform Admins use
**Admin → Emails** to edit drafts, publish versioned templates, preview only
safe sample links, send themselves a test, and review redacted delivery status.
Templates may only use the placeholders declared for each notification and
`{% if %}` conditions, and render in Jinja's sandbox. Rendered messages and
account links are encrypted at rest; a queued email whose sign-in or invitation
link has been used or has expired is not sent, and the content of finished
emails is erased after 30 days.

Every email uses one fixed layout, so they all look alike: the logo, the message
in a white card with one button, and a footer. Admins edit only the message;
the **Branding** setting on Admin → Emails shows or hides the logo and can use
another https image. The default is the V symbol without the wordmark or a
background, so it stays clean on light and dark surfaces. Its SVG source has a
high-resolution transparent PNG export for use in email clients. Browser
previews load the bundled mark from the current site; delivered emails use an
absolute image URL under `PUBLIC_BASE_URL`. Mail clients that block images show
the VoxBento alternative text until images are allowed.

Besides sign-in, invitation and hosting emails, people are
told when they are removed from a team, when an Admin changes their Admin,
hosting, active or verified status, when their password is set, changed,
removed or reset, and when their account is deleted. Team invitation links last
7 days. Shareable booth invite links send no email.

## Security Layers

Publishing audio to a booth is protected by three independent enforcement layers:

<Tabs>
  <TabItem value="role-and-active-interpreter-check" label="Role and active-interpreter check">

Voxbento's server-side coordination layer rejects any attempt to activate a microphone or begin audio publishing unless the participant's role can go live (every role in `portal/roles.py`: Interpreter, Room coordinator, Event owner, Admin) **and** they are the currently designated active broadcaster for that booth. Standby participants and listeners cannot publish audio.

</TabItem>
  <TabItem value="whip-url-gating" label="Publish tickets">

Before the browser can start publishing, it asks the portal for a publish ticket over its booth WebSocket. The portal issues one only to the active interpreter, and only while Mission Control has the booth live. The ticket is single-use, expires after 30 seconds and is bound to that booth's MediaMTX path. MediaMTX passes it to the portal's private authorization hook, which redeems it and checks again that its holder is still the active interpreter and that the booth has not been stopped. A WHIP request without a valid ticket, such as an anonymous POST straight to MediaMTX, is refused with HTTP 401 and cannot displace the live interpreter.

</TabItem>
  <TabItem value="media-server" label="Media server">

MediaMTX is configured to allow only one publisher per stream path at a time. Even if a stale or unexpected session somehow reaches the media server, it immediately displaces any existing publisher — ensuring a single, authoritative audio source at all times.

</TabItem>
</Tabs>

Password sign-in requires a verified email address. `/login` allows 10 attempts
per email address per hour.

## Program floor source

An optional program-ingest mode replaces only the Jitsi audio adapter. The encoder
sends a separate HTTPS WHIP output to MediaMTX's canonical event/room/floor path;
YouTube receives its own independent output. FastAPI authorizes publishing through
MediaMTX's internal HTTP callback and reconciles room-owned transcription workers.
The reconciler reads one MediaMTX path snapshot per tick, and per-room ownership
locks keep an unavailable room from delaying authorization for other rooms.
Credential revocation commits before media cleanup; if cleanup is temporarily
unavailable, the old token stays invalid while reconciliation retries the kick.
While a dependency stays down, the reconcilers log the outage once, remind every
5 minutes and log its recovery, rather than repeating a warning on every 2 s retry.
Media never passes through FastAPI. Only one floor source may own a room.

The existing FFmpeg/STT/aggregator/storage/translation/TTS chain is reused. Program
segments retain IDs, a persistent room sequence and receive-time metadata into
translated text and synthesized speech. Listener-side delay aligns these with an
external video; inference is never intentionally delayed. This is approximate
manual synchronization, not shared encoder timecode.

See the repository's `docs/program-stream-ingest.md` for rollout, security limits,
encoder compatibility, capacity and the required two-destination rehearsal.

### RTMPS relay mode

A room can choose relay mode instead: the encoder sends a single RTMPS stream
(H.264 + AAC) to MediaMTX on the same canonical floor path, authorized per room by
the same callback with a stream key bound to the RTMPS transport. A dedicated
`program-relay` service pulls the floor over private RTSP and pushes it with
`ffmpeg -c copy` to the room's YouTube RTMPS destination, while the existing
pipeline consumes the audio. The portal reconciler drives the relay service over an
authenticated control API and stops relays on revoke, source switch, destination
removal or restart; it enforces a fail-closed relay cap. The YouTube key is
Fernet-encrypted at rest and write-only. Ingest, relay and language-processing
health are reported separately. Relay mode puts VoxBento in the YouTube path, so
the independent WHIP mode remains the default. See `docs/program-relay.md`.

## Production deployment

Production deployment builds and validates a separate candidate checkout before
updating the live checkout. The portal reads code and dependencies from its Docker
image and receives `.env` settings through Compose. See the
[deployment preflight](configuration/deployment.mdx#deployment-preflight).

For self-hosted domains, set `PUBLIC_BASE_URL` to your public URL; the default is
`https://voxbento.com`. This is the same setting used for email links. Public
`GET /sitemap.xml` builds canonical URLs from `settings.public_base_url`, never
from the request's `Host` header. It strips trailing slashes before appending the
existing sitemap paths and XML-escapes the resulting URLs.

A configured path prefix is preserved in sitemap entries: for example,
`PUBLIC_BASE_URL=https://interpret.example.com/voxbento/` produces
`https://interpret.example.com/voxbento/` for the home page and
`https://interpret.example.com/voxbento/research` for the research page.
