The Voxbento API uses bearer token authentication. You call the `voxbento.com` token endpoint once with your booth access token, receive a signed JWT in return, and then include that JWT as an `Authorization: Bearer {token}` header on every subsequent request. Tokens expire after 24 hours by default, at which point you request a fresh one.

## Binding an OAuth exchange to an event

OAuth integrations using `/oauth/token` can send an `event` form field with
`grant_type=authorization_code`. Its value must be the event slug retained by
the integration's server when the flow started, alongside its validated OAuth
state. Do not take this value from the returning browser or consent form.

VoxBento checks that slug against the authorization code before consuming the
code, creating tokens, or granting event membership. A mismatch returns HTTP 400
with `error: "invalid_grant"`. Both successful authorization-code and refresh-token
responses include `event`, the slug bound to the issued token.

The parameter is optional for compatibility. Existing clients keep working, but
omitting it does **not** prevent an event swap. Deploy the VoxBento support first,
then update Eventyay or another integration to send its server-retained event on
every authorization-code exchange. Also verify the returned event before storing
the tokens. Checking only the response is too late to prevent a membership grant.

## Obtaining a Token

Send a `POST` request to the Voxbento token endpoint with a JSON body containing the `token` field set to your booth access token. The `BOOTH_ACCESS_TOKEN` value is provided by the Voxbento platform.

**Endpoint**

```
POST /api/auth/token
```

**Request body**

```json
{
  "token": "your-booth-access-token"
}
```

**Response**

```json
{
  "access_token": "eyJ...",
  "token_type": "bearer"
}
```

**Example request**

<Tabs>
<TabItem value="curl" label="cURL">

```bash
curl -X POST https://voxbento.com/api/auth/token \
  -H 'Content-Type: application/json' \
  -d '{"token": "your-booth-access-token"}'
```

</TabItem>
<TabItem value="python" label="Python">

```python
import httpx

response = httpx.post(

```

:::info
The `BOOTH_ACCESS_TOKEN` is provided by the Voxbento platform. Ensure you have the correct credentials before attempting to authenticate.

This is a global legacy API credential. The JWT issued by `/api/auth/token` has global scope across the applicable protected legacy `/api/events/...` endpoints; it is not restricted to a single event. Treat the credential and issued JWT as highly sensitive, and share them only with trusted integrations. This scope does not grant access to every application route or bypass separate authorization checks.
:::

## Using the Token

Include the token you received as a bearer credential in the `Authorization` header of every subsequent API request.

```
Authorization: Bearer eyJ...
```

**Example — listing booths for an event**

```bash
curl https://voxbento.com/api/events/pycon2026/booths \
  -H 'Authorization: Bearer eyJ...'
```

Store the token in a secure location such as an environment variable or a secrets manager. Do not embed it in client-side code or version-control it.

## Token Lifetime

:::tip
Request a new token proactively before your current one expires to avoid a gap in service. Checking the response status on each request and refreshing on a `401` is a safe fallback strategy.
:::

Tokens expire after 86400 seconds (24 hours) by default. When a token expires, the API returns a `401 Unauthorized` response — simply call `POST /api/auth/token` again to obtain a fresh token and retry the original request.

## Error Responses

| Status | Meaning |
|---|---|
| `401 Unauthorized` | The `Authorization` header is missing, the token is malformed, or the token has expired. Request a new token and retry. |
| `403 Forbidden` | The token is structurally valid but the request targets a resource you are not permitted to access. |

## Cookie-Based Authentication (Internal UI)

While external integrations use the Bearer tokens described above, the Voxbento frontend UI relies on a strict hierarchy of HTTP-only JWT cookies to authenticate users.

### The Token Hierarchy

Voxbento issues two HTTP-only JWT cookies, and booth-facing paths consider
both of them together:

1. **`user_token`**: Issued when a registered user logs in (via `/login`). It contains claims about their identity (`sub`) and whether they have site-wide admin rights (`is_admin=True`).
2. **`session_token`**: Issued when a user clicks a magic invite link (`/join/{token}`). It is scoped to a specific `event_slug`, `room_id`, and `language_code` with a specific role.

A logged-in user who redeems an invite keeps both cookies. The interpreter
lobby lists the union of their database memberships and their invite grant,
and booth pages resolve access from all valid sessions at once, so the login
session never hides ("shadows") the invite. Invite role claims only apply to
the booth they are scoped to (matching event, room, and language).

### Role Resolution (`resolve_booth_role`)

When a user joins a booth via WebSocket, the backend `resolve_booth_role` function determines their ultimate permissions by checking the database and comparing their tokens.

VoxBento's roles, highest first, are defined in `portal/roles.py`:
`admin` > `event_owner` > `room_coordinator` > `interpreter`

Each role holds every permission of the roles below it, so when a user has several roles here (for example an `interpreter` invite link while signed in as the event's owner) **the highest one wins**, which equals their combined permissions. The Admin role is read from the account in the database, so a demoted Admin loses it immediately.

### Access checks

HTTP routes use FastAPI dependencies named after the people they let in. Admins pass every check.
1. `require_admin`: Admins only (`/admin/users/`, hosting access, developer apps).
2. `require_event_owner`: owners of the event in the URL path.
3. `require_owner_or_coordinator`: owners of the event or coordinators of the room in the URL path.
4. Anyone else gets HTTP `403 Forbidden`.
