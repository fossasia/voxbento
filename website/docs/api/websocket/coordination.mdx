The Voxbento coordination layer runs entirely over WebSockets. This connection dictates who is allowed to hold the microphone (WHIP authorization), manages the real-time participant roster, and facilitates instant chat.

## Connection & Authentication

To join a booth's coordination room, establish a WebSocket connection to:

```text
/ws/booth/{booth_id}
```

### Authentication (Tokens and Cookies)
When establishing the WebSocket connection, `resolve_ws_auth` resolves credentials as follows:
- The **`?token=` query parameter** containing a JWT (either a participant token or a user JWT). Note that if an invalid `?token=` parameter is provided, it takes precedence and immediately closes the socket with close code `4001`, even if a valid session cookie exists.
- **HTTP cookies** (`session_token` or `user_token`), checked as fallback when `?token=` is not provided.
- If credentials are missing altogether, the connection handshake is still permitted when `BOOTH_ACCESS_TOKEN` is unset (local development). When `BOOTH_ACCESS_TOKEN` is configured, missing credentials immediately close the socket with code `4001`.

The server decodes verified credentials to determine the user's role (`interpreter`, `room_coordinator`, etc.) and identity. **The client cannot assert its own role; the server solely trusts the server-verified JWT claims.**

### Authorization changes and revocation

Booth broadcasts are delivered only to sockets holding a supported role for that booth. A socket that is unauthenticated, holds a role for a different booth, carries an unsupported role, or has been revoked stays connected but receives no booth state, chat, or handoff messages.

If an account is demoted from Admin, deactivated, or deleted, the server revokes its live booth sockets and closes them with close code `4003`. Deactivated or deleted accounts cannot re-authenticate over WebSocket, even if their token has not expired. Live revocation is process-local and assumes the documented single-worker/single-replica deployment. Invite-link sessions are bearer capabilities rather than account sessions, so account changes do not revoke them. Membership removal closes affected booth sockets, and current permissions are resolved again on connection. Broadcast delivery also rechecks membership; a database-check failure withholds that message without revoking otherwise valid sockets.

Apply Alembic migrations 036–038 before starting the updated portal. Existing
invite links retain their tokens; new participant sessions carry a separate
public invitation ID so revoking the invitation can close its sockets. Older
participant JWTs without that ID remain valid until expiry and cannot be
individually revoked by this mechanism. Account-based sockets are unaffected by
that invitation compatibility exception.

## Outbound Messages (Client to Server)

All messages sent from the client to the server are JSON objects with a `type` field. Every other field sits next to `type` at the top level; there is no `payload` wrapper.

### 1. Join a Booth
The first message sent after connection MUST be `booth:join`. The server will not broadcast your presence or send you state updates until this is received.

```json
{
  "type": "booth:join",
  "display_name": "Arnav Angarkar"
}
```

### 2. Update Status
Participants should continually update the server on their WebRTC status.
```json
{
  "type": "booth:update-state",
  "mic_active": true,
  "ingest_connected": true
}
```

### 3. Send a Chat Message
Sending an internal chat message to the booth.
```json
{
  "type": "booth:chat",
  "body": "Ready in 30 seconds."
}
```

### 4. Request WHIP Publish Ticket
Before an active interpreter can publish media via WHIP, they must request a single-use publish ticket:
```json
{
  "type": "booth:request-publish-ticket"
}
```
The server validates that the participant holds the active interpreter role and that the booth is broadcasting, then responds directly with:
```json
{
  "type": "booth:publish-ticket",
  "ticket": "ticket-token-string"
}
```
The browser sends this ticket as `Authorization: Bearer <ticket>` in its WHIP HTTP POST request to MediaMTX.

### 5. Initiate a Handoff (Set Active)
This message designates a new active interpreter in the booth.

```json
{
  "type": "booth:set-active",
  "target_id": "participant-uuid-here"
}
```
**Authorization Policy:** Handled by `BoothRegistry.set_active_interpreter`:
- Joined interpreters may select themselves (`requester_id == target_id`) to take over as active interpreter, even if they lack the `BOOTH_SET_ACTIVE` permission.
- Room coordinators, Event owners and Admins (every role with `BOOTH_SET_ACTIVE` in `portal/roles.py`), or the currently active interpreter, can assign any joined interpreter as the new active interpreter. Each participant in `booth:state` carries `can_go_live` and `can_set_active`, so clients never compare role names.
- If an unauthorized participant attempts to reassign another participant, the server rejects the request and sends a `booth:error` message back to the client.

Coordinators and interpreters can also utilize the structured handoff flow using `booth:initiate-handoff`, `booth:accept-handoff`, and `booth:cancel-handoff`.

## Inbound Messages (Server to Client)

### 1. `booth:state` (The Source of Truth)
Every time a participant joins, leaves, updates their mic status, or the active interpreter changes, the server broadcasts a `booth:state` message to all connected clients.

```json
{
  "type": "booth:state",
  "state": {
    "booth_id": "pycon2026-14-en",
    "active_interpreter_id": "participant-uuid-here",
    "ingest_status": "disconnected",
    "participants": [
      {
        "participant_id": "participant-uuid-here",
        "display_name": "Arnav Angarkar",
        "role": "interpreter",
        "mic_active": false,
        "ingest_connected": false,
        "can_go_live": true,
        "can_set_active": false
      }
    ]
  }
}
```
Clients use this payload to render the participant list and determine if they are authorized to fetch the WHIP URL.

### 2. `booth:chat`
Received when another participant sends a message.

```json
{
  "type": "booth:chat",
  "message": {
    "message_id": "message-uuid",
    "sender_id": "participant-uuid",
    "sender_name": "Arnav Angarkar",
    "body": "Ready in 30 seconds.",
    "sent_at": "2026-06-16T10:00:00+00:00"
  }
}
```

## The Complete Handoff Flow (Under the Hood)

When a `room_coordinator` clicks "Set Active" in the UI, here is the exact sequence of technical events:

1. **WS Request:** Coordinator sends `booth:set-active` with the target's ID.
2. **Server Auth:** The `_handle_set_active` backend function verifies the coordinator has `BOOTH_SET_ACTIVE` permissions.
3. **State Update:** The server updates the in-memory `BoothRegistry` and immediately broadcasts a new `booth:state` to all clients.
4. **Active Interpreter Notification:** The incoming interpreter's client sees they are now the `active_interpreter_id`.
5. **Publish Ticket Request:** The browser sends `{"type": "booth:request-publish-ticket"}` over the WebSocket.
6. **Ticket Issuance:** The server verifies that the participant is active and broadcast is unlocked, issuing a single-use 30-second ticket (`booth:publish-ticket`).
7. **Media Disconnection & Seamless Switch:** The incoming interpreter sends an HTTP POST with their WebRTC SDP offer to the WHIP URL with `Authorization: Bearer <ticket>`. MediaMTX verifies the ticket with `/internal/media-auth`, accepts the new connection, and using `overridePublisher: yes` kicks the old publisher, ensuring listeners experience sub-second handoff without reconnection.
